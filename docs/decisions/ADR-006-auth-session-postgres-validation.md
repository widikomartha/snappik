## Proposed architecture and identity guarantees

Retain the [candidate session contract](../auth/SESSION_CONTRACT.md): Better Auth owns credential, session, account and verification data in a restricted auth namespace; business users remain separate. App key `(auth_provider, auth_subject)` represents `(configured issuer namespace, immutable subject)`: `better-auth:<AUTH_INSTANCE_ID>` plus library user UUID. Upstream account key is fixed configured provider ID (permanently bound to one issuer) plus validated upstream subject. Never use a contact email, request Host, display name or provider label supplied by the browser as identity. Managed fallback uses canonical tenant issuer + validated `sub`. Namespace/provider replacement requires explicit migration, never email matching.

Disable implicit account linking; no public MVP linking route. Future explicit linking proves both accounts, fresh primary reauthentication (5 minutes), same-origin initiation and state binding; operators also need recent TOTP. Reject accounts already bound elsewhere. **New observed gap:** generated 1.7.9 PG schema accepts duplicate `(providerId,accountId)`. A spike-only unique index rejects them; reviewed production schema must include equivalent uniqueness, collision handling and races before linking/callback integration. Existing app mapping uniqueness alone cannot fix duplicated provider accounts.

Owner login requires verified email. Return URL is path-only allowlisted `/app` segments, <=512 characters, no query/fragment/encoding/traversal; sanitize before protected state, fallback `/app`, and never replace with callback query. Operator `/ops` has a separate exact allowlist. Auth APIs remain under `/api/auth/*`; business APIs return JSON 401/503, not login HTML. Use only reviewed handler allowlists, not an automatically exposed full library API surface.

Session is fixed one hour with refresh/cookie cache disabled. Use signed opaque, host-only Secure/HttpOnly/SameSite=Lax cookie, Path=/, no browser token storage. Server/DB recheck expiry at `now >= expires_at`, verification, revocation, security version, current membership and permission. Origin/CSRF checks must cover login/reset/logout/link/factor mutations; library [security defaults](https://better-auth.com/docs/reference/security) do not replace the application's exact-origin policy. Exempt protocol callbacks only through validated state/PKCE/provider proof. No auth feature is authorized by cookie presence in proxy/middleware.

Logout commits shared revocation before success, clears MFA assurance, then cleans library rows/cookies. Real PG now confirms normal deletion survives another process/DB restart, but also confirms raw library 200 on deletion failure. Implement the existing user-lock/security-version design and fail uncertain storage with 503; never route raw sign-out directly to production. Reset uses library single-use 15-minute token, generic known/unknown response, no auto-login, all-device revocation and durable mail enqueue. Successful native PG reset revocation and synchronized token consumption were observed; app reset-version transaction, delivery/timing/throttles and concurrent login/reset are still missing. OAuth-only owner recovery stays upstream.

Operator permission remains in platform_roles, independent of studio membership, email domain and provider organization roles. After successful TOTP, persist method/time against the **current session and security version**; require totp age <15 minutes for every ops entry/data boundary, including OAuth, with no trusted-device or backup-code bypass. For the smallest pilot proposal, bootstrap credential + verified-email + TOTP operator accounts through a controlled process; OAuth-only operator enrollment remains disabled until fresh upstream reauthentication/enrollment is verified. A password reset never restores operator authority or clears MFA. Lost factor suspends ops, revokes sessions, verifies identity through a named recovery owner, reenrolls and audits before regrant. The named owner/process and real authenticator drill remain approval/evidence gaps.

## Secrets, deletion, operations and lock-in

Use canonical APP_ORIGIN/BETTER_AUTH_URL, stable AUTH_INSTANCE_ID, CSPRNG server-only BETTER_AUTH_SECRET (minimum 32 characters), separate constrained AUTH_DATABASE_URL and migration role, and approved mail credential reference. OAuth adds fixed issuer/client ID plus server-only client secret; no Drive scopes. No NEXT_PUBLIC secret, token URL/cookie logging, secrets in handoffs or environment discovery from unrelated stores. Shared replicas use coordinated keys; rotation must preserve factor/token decryptability and rehearse invalidation. App startup/config wiring, production grants and rotation are not implemented by this investigation. Existing app fail-closed config remains unchanged.

Library handles account password hashes (observed locked scrypt N=16384, r=16, p=1, 64-byte output, random 16-byte salt in prior evidence). Snappik owns resource benchmarking, reviewed parameter choice and distributed abuse limits. Hash cost on a laptop does not predict the funded host; retain this as a closure gate. App users never contain hashes. Gallery password hashing is independent and outside this task.

Provider deletion capability is not a complete deletion policy. Keep raw delete-user endpoints inaccessible pending DEC-006 orchestration: verify requester, suspend/revoke access, handle sole-owner studio/business records and retention, then remove auth account data; restore must reapply deletion. Preserve required audit evidence without logging credentials. Trial eligibility on deleted/recreated accounts, processor/backup expiry and jurisdiction need product/legal decisions, not an incidental auth hook. No deletion flow was executed.

Self-hosted auth reduces service coupling but retains library-schema/hash/encryption coupling and operational responsibility. Export/migration must preserve app user IDs, memberships, operator grants, namespace mapping and immutable history; do not assume password hashes/factors are portable. Auth0/Supabase additionally couple tenant APIs, token/claim semantics, plan limits and provider recovery. Budget must include web/worker/PG, delivery, monitoring, backups and operator time. No deployment budget exists in verified files; do not describe Better Auth as cheapest or managed Free as production-sufficient.
