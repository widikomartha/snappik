# ADR-009: durable revocation and local authentication boundary

Date: 19 October 2026 (Asia/Makassar). Status: **implemented and locally validated subset; DEC-001 OPEN/PARTIALLY VALIDATED**. Supplements [ADR-006](ADR-006-auth-session-postgres-validation.md); historical ADR-004/006 findings are not overwritten. Production provider/deployment selection remains conditional.

## Context and decision

Actual startup was clean local master / `829a46b`; DEC-002/003 documentation commits were preserved. The user authorized authentication hardening, safe migrations and the next feasible local integration, excluding commits, external connections, deployment and destructive operations. Native Better Auth 1.7.9 logout can swallow session deletion failure; its generated account schema lacks provider/subject uniqueness. Earlier synthetic investigations are retained rather than repeated unchanged.

Use a **durable application revocation record**, separate from physical library cleanup. A server-only Better Auth session-create hook attaches the immutable library user UUID to app users through `(better-auth:<AUTH_INSTANCE_ID>, subject)` and inserts owner_session_security. It does not provision/renew a studio or trial. Missing metadata fails closed; an existing revoked row is never restored by attachment retry. Native session deletion cascades metadata; the old token cannot resolve once the native row is absent.

Every configured session lookup uses the native signed cookie plus PostgreSQL metadata/current security_version/verified email/expiry. A server-only assertActive closure rechecks under the **same app user row lock and transaction** used by the implemented onboarding services, before data work and before commit. Lock order is user → metadata → studio → project → selection set. Authentication never trusts browser JSON, email joins or cookie presence. Existing foundation-only VerifiedOwner helpers are still synthetic internal seams, not new authenticated product endpoints.

Logout validates exact Origin, then commits revoked_at and clears MFA assurance under that user lock. Storage/commit uncertainty yields 503, no success or cookie clearing. Successful revocation permits 200 even if later physical cleanup fails: all Snappik guards deny that remaining native row. Retried logout is idempotent. Cookie/state headers are cleared only after certainty. Raw library get-session/sign-out must never bypass the wrapper. Library APIs remain server-only, not general product APIs.

## Schema and duplicate handling

[Separate reviewed migrations](../../src/db/auth-migrate.ts) use an auth advisory lock/checksum journal without modifying committed app 001/002 migrations or their compatibility floor:

1. [Auth baseline](../../src/db/auth-migrations/001_better_auth.sql): fixed 1.7.9/twoFactor schema in snappik_auth, generated once on a new synthetic cluster and committed as reviewable SQL. No runtime generator.
2. [Account uniqueness](../../src/db/auth-migrations/002_account_identity.sql): lock account writes, detect **any** duplicate `(providerId,accountId)`, abort with a redacted code, otherwise add a unique constraint. No survivor selection, deletion, account/user merge or trial change. Concurrent inserts serialize on the constraint.
3. [Security metadata](../../src/db/auth-migrations/003_session_security.sql): FK to native session and app user, version/revocation/MFA metadata, indexes and PUBLIC denial. Existing native sessions lacking metadata remain unauthorized; no automatic session backfill.

An already journaled baseline containing duplicates is tested: migration stops with rows unchanged and no 002/003 journal entry. An unmanaged pre-existing auth schema is **not automatically adopted**: baseline creation fails rather than assuming compatible fields. A migration owner must review schema/history and duplicates offline; no destructive repair tool is supplied. Resolve an actual collision by a separately authorized identity investigation, never an email merge. Public-schema historical spike tables are not moved or changed.

The [auth grant template](../../src/db/auth-grants.sql) extends trusted web service grants. SQL probes verify allowed auth access and denial of DDL, metadata reassignment, journal edits and operator self-grants. This is trusted service authorization, not RLS or deployed IAM; actual credential-role separation remains a deployment task.

## Next.js slice and configuration

Root dependencies pin Better Auth 1.7.9 and Kysely 0.29.6, reusing inspected/cached packages. The library candidate is still **not a production version approval**; 1.7.10 was previously observed and upgrades/advisories remain a release gate. Explicit dialect/schema selection and migration readiness precede library initialization (eager initialization before tables exist cached a schema failure during implementation).

Default AUTH_MODE=unconfigured still fails closed. Explicit **better-auth-local** permits only loopback app and database hosts, a stable validated AUTH_INSTANCE_ID and server-only BETTER_AUTH_SECRET >=32 characters. Optional BETTER_AUTH_URL must exactly equal APP_ORIGIN. There is no production mode, test-login HTTP endpoint or real mail/provider connection. CLI migrations enforce the same local target database, use a separate migration credential if supplied, and never run during web startup. Both app and auth pools are bounded by DB_POOL_MAX: at most twice that value per web process (default total 10), plus workers/migration reserve; target capacity is untested.

Implemented Next `/api/auth/*` allowlist: POST sign-in/email, sign-out and two-factor/verify-totp. JSON/body/field/Origin checks, request IDs, no-store/no-referrer, token-redacted responses. Session expiry is fixed one hour, refresh/cookie cache disabled. Browser cookie is HttpOnly/SameSite=Lax/host-only; **HTTP loopback uses a non-Secure cookie solely for local verification**. HTTPS Secure/proxy/browser behavior still requires approved target evidence. `/login` has a credential/TOTP form; owner pages use the guarded adapter, and app/setup/suspended views expose retry-aware logout. Signup, account management, native session introspection, OAuth/social/callback and linking routes are not publicly exposed. Recovery routes return 503 RECOVERY_NOT_CONFIGURED, and `/recover` remains honest about missing delivery.

Implicit linking is disabled. Actual library callback/link tests with synthetic exchange/profile plus real PG verify explicit linking preserves user/mapping, implicit same-email collision fails and a second user cannot take over the key. Public explicit linking remains inaccessible until fresh reauthentication/state/audit requirements pass; no signed provider proof is inferred.

Operator checks require current platform_roles permission plus persisted current-session/current-version TOTP <15 minutes old; enrollment, another session, backup code or trusted-device flag cannot authorize ops. Successful wrapper TOTP binds assurance; trustDevice input is rejected. Factor enrollment/change endpoints remain inaccessible. No operator business route or bootstrap/recovery workflow is added. Password recovery/reset/version orchestration and pending challenge lifecycle across logout/reset remain separate unverified recovery/MFA gates; clearing browser challenge cookies alone is not a claim of copied-challenge revocation.

## Alternatives, limitations and reconsideration

Native deletion alone was rejected because its false success is reproduced. Cookie clearing or memory tombstones were rejected because they cannot prove cross-process denial. Physical deletion in the security transaction would conflate durable denial with cleanup failures. Native library code is not patched or vendored; future upgrades must retain the wrapper guarantees. Auth0 stateful sessions remain the managed fallback from ADR-006, requiring their own funded/provider tests.

A response authorized/committed before logout obtains the user lock may already be in flight; it cannot be recalled. Mutations that lose that ordering must recheck and fail. If DB connectivity fails, previously issued cookies may become valid again after recovery **when no revocation committed**; the UI reports uncertain logout/retry, not success. Lost commit acknowledgements require retry; guards read shared state and never serve cached stale authorization. Direct library APIs are not evidence of app permission. All-device reset, key rotation, durable distributed throttles, secret compromise, deletion/restore reconciliation and hosted multi-replica behavior remain unverified.

[Current evidence](../auth/DEC-001-EVIDENCE-2026-10-19.md) records real PostgreSQL/Next/worker and browser results, initial failures and exclusions. Full T-001/T-002/T-003/T-015 and BL-001/003/004 remain incomplete. DEC-001 closes only with every register criterion: approved provider/target budget, signed callback/protected route, delivered recovery and races, operator MFA/recovery, secret/hash/throttle/rotation and constraints evidence. Local fixtures cannot substitute. No third-party price/terms claim is refreshed in this implementation; ADR-006 prices retain their access date.
