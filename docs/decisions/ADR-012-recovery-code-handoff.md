# ADR-012: recovery proof outside navigation URLs

Date: 19 October 2026 (Asia/Makassar). Status: **implemented local candidate; DEC-001 OPEN/PARTIALLY VALIDATED; production approval pending**. Supersedes the fragment-handoff portion of [ADR-011](ADR-011-browser-recovery-boundary.md) and ADR-010, retaining their historical evidence and all other invariants. Starting actual main / `0fc60a1`, clean. Scope: DEC-001/BL-001, REQ-AUTH-001/REQ-REL-001/REQ-UX-001, BR-REL-001/002, BR-TEN-001 and BR-OPS-001; T-001/003/015/016 subsets. No provider, dependency or schema replacement.

## Problem, minimum capabilities and alternatives

The previous real-browser probe demonstrated original fragment URLs in global history after current-entry cleanup. A fragment avoids ordinary HTTP request paths but does not establish history secrecy. Minimum: generate no navigation URL containing recovery authority; keep cross-device recovery, 15-minute single-use high-entropy proof, generic request responses, durable encrypted delivery, atomic password/version/session reset and unchanged MFA. No external sender/account is authorized.

| Alternative | Security and usability | Persistence, delivery and operations | Disposition |
|---|---|---|---|
| Existing fragment links with earlier scrubbing | Convenient across devices; bearer still enters original navigation/history, extensions and inbox. Query links additionally expose HTTP paths. Earlier cleanup cannot meet the no-bearer-navigation criterion | Existing tables/outbox; sender link scanners may open links; current GET does not consume proof | Baseline compared; rejected for newly generated handoffs |
| Manual single-use code plus clean fixed link | No authority in navigation URL; user pastes a case-sensitive43-character base64url code, including on another device. Longer than a numeric PIN; accessible labels/ID-EN instructions required. Inbox/clipboard/DOM/POST and phishing remain threats | Reuses32 random bytes, SHA256 lookup, AEAD payload, retries, expiry and same reset transaction. No migration, challenge cookies or new recovery session. Future email must send separate code text and clean link, never append code for tracking/convenience | Preferred local candidate: smallest change satisfying the criterion |
| Browser/session-bound challenge plus code exchange | Can scope short-code attempt budgets and keep final proof in HttpOnly cookie; first proof still needs safe entry. Requiring initiating cookie prevents lost-device/cross-device recovery without a transfer flow | New durable challenge/attempt/expiry/exchange states, CSRF/cookie/fixation and concurrent exchange tests; extra round trip and restart semantics | Defer until an evidenced product or abuse-control requirement justifies complexity |

Fallback: keep recovery unavailable without its configured key and use the upstream provider for upstream-only accounts. Do not silently restore token URLs. Six-digit PINs are not a drop-in substitute: their entropy requires separately designed durable guessing limits/challenge binding. Managed Auth0 remains a broader DEC-001 alternative; changing providers does not remove URL leakage by itself.

## Local decision and compatibility

Synthetic delivery receives `{id,email,url,code}`; `url` is exactly `${APP_ORIGIN}/recover?step=reset`, with no user/credential identifier. `step=reset` selects only a public form; it grants no authority. `code` is the existing43-character credential, supplied separately. Existing encrypted v1 queued payloads still decrypt and deliver in this format. No acknowledged outbox row is discarded, re-keyed or regenerated by this change; retries repeat the same job/code. A previously sent token URL cannot be recalled. Its credential retains its original expiry/single-use semantics and can be entered manually until invalidated. No existing user data or migration history changes.

The form accepts code and new password, sends only the existing exact POST `{token,new_password}` DTO with Origin/JSON guards, and never auto-submits from a URL. Legacy fragments and unsupported query parameters are rejected and scrubbed; raw URL proof is not retained in the early bridge. The bridge holds only request/reset/invalid mode. Clearing a user-supplied bad URL is best effort, not retroactive history/proxy-log erasure. Refresh requires code re-entry; retries retain input only in the active form; success clears fields and the non-secret step hint. No code in React keys, local/session storage, history.state, return URLs, public responses or normal logs.

Better Auth1.7.9 still owns native password hashing; the existing wrapper owns proof consumption/version/revocation in one PostgreSQL transaction. Native reset and account-linking APIs stay closed. Credential gate, session user-lock order, account uniqueness, onboarding and TOTP are unchanged. All user proof/session invalidation and outbox fencing/retry/terminal erasure remain ADR-010. This is a delivery/browser protocol change, not a claim that a manual bearer code becomes non-bearer authentication.

## Threat model, limitations and release gates

Verified prior failure: global history retained original fragment navigations. Current implementation prevents newly generated handoffs from putting the credential there. It cannot remove old history, email archives, synchronization, pasted URLs or screenshots. No browser history deletion is attempted. Ordinary referrers exclude fragments, but scripts/extensions can read original location before cleanup; query credentials can reach a proxy before any JavaScript runs. The manual flow removes the source of that exposure for normal generated links.

Clean-link GET, prefetch and preview navigation do not consume credentials or mutate password state. A scanner that reads the whole email can still obtain the code. Compromised inbox/device, phishing, XSS, privileged extensions, clipboard managers, browser autofill/session restore and POST body capture remain risks; autocomplete=off and password masking are best efforts. No third-party analytics or sender tracking was added. Actual sender tracking, hosted HTTPS/proxy/body-log suppression, CSP/extension/device behavior, email preview/scanners, separate physical devices and timing/shared-abuse defenses need approved environment evidence. Never send code in telemetry or template URLs.

See [executed evidence](../auth/DEC-001-HANDOFF-EVIDENCE-2026-10-19.md) for exact Passed/Failed/Blocked/Not-run distinctions. Neither local tests nor this ADR approve production UX/security/provider choice. User-owned gates: acceptance of manual-code production UX/risk, sender/host/budget and named operator recovery owner. Routine local protocol, tests and documentation are within the current request. Reconsider on shorter-code requirements, sender integration, browser/provider upgrades, recovery-session design, multi-tenant load or an actual new exposure finding.
