# ADR-010: atomic password recovery and encrypted notification outbox

Date: 19 October 2026 (Asia/Makassar). Status: **implemented local subset; DEC-001 OPEN/PARTIALLY VALIDATED**. Supplements [ADR-009](ADR-009-auth-local-hardening.md) and ADR-006; no production provider choice or deployment approval.

## Context and criteria

Resume inspected local master / `829a46b` with the previous uncommitted hardening implementation intact. Recovery was intentionally unavailable. The user authorized local recovery/reset, durable retries and PostgreSQL concurrency validation, excluding external delivery, commits and deployment. Scope: REQ-AUTH-001, REQ-REL-001, REQ-TEN-001, REQ-OPS-001; BR-REL-001/002, BR-TEN-001, BR-ONB-001, BR-ENT-001, BR-OPS-001; T-001/002/003/015 subsets, not full acceptance.

Minimum capabilities: durable accepted requests; generic known/unknown responses including storage failures; secret-safe single-use 15-minute tokens; atomic credential change/version/revocation; no stale password/TOTP proof crossing reset; bounded delivery retries with restart/fencing; preserved business identity/data. Reuse Better Auth 1.7.9 hashing and existing PostgreSQL session guard; no new auth provider or password algorithm. Installed native password/TOTP/session code and existing tests are the implementation evidence. No pricing/version/third-party capability research was repeated or updated in this slice.

## Decision

Add reviewed auth migration [004](../../src/db/auth-migrations/004_password_recovery.sql), leaving app 001/002 and auth 001/002/003 unchanged. Native account table still owns the library password hash. The [recovery orchestrator](../../src/modules/auth/recovery.ts) calls the library password hasher and updates its pinned credential row in the same PostgreSQL transaction as token consumption, app security_version increment, durable session revocation and assurance clearing. It does not reset enrollment, permissions, studios, trials or acknowledged records. All outstanding tokens for that user and queued/running notifications are invalidated. No automatic login. Library recovery/reset APIs are never mounted directly.

A [credential gate](../../src/modules/auth/gate.ts) holds one PostgreSQL transaction advisory lock across local password proof/session attachment, pending TOTP creation/consumption, recovery issuance and reset. Reset additionally locks the mapped app user before credential/session writes; existing authorization/logout use that same user lock. This prevents a pre-reset proof from receiving the post-reset security version. Pending native `2fa-*` and trusted-device proofs for the subject are deleted without deleting factors. Raw server-only library helpers are fixture/internal capabilities, never general application authorization APIs. Future OAuth/link/factor routes need equivalent orchestration before exposure.

This is deliberately a **local, low-throughput baseline**: one in-flight credential operation per adapter instance; local contention returns generic retryable 503 rather than an unbounded queue. Other processes wait at most the 5-second advisory lock timeout. No external work runs under this lock. App pool minimum is 2 because native session attachment needs another connection. Existing session reads/business work remain independent and serialize on the user row. Prefer correctness over a premature per-account distributed challenge protocol; before shared SaaS, benchmark contention and design/retest any narrower fence. Native proof/session creation uses separate transactions; failure before response can leave an undisclosed session/challenge row, but no cookie is returned and business guards remain authoritative.

Recovery request `{email,request_id}` uses a client UUID v4 for response-loss retries. Same address+ID dedupes; address budget is 3 accepted unique requests/hour with the same behavior for known, unknown, unverified and OAuth-only accounts. Every admitted request writes a receipt, token row and encrypted outbox job. Ineligible users get null subject and an empty recipient; their jobs never call delivery. This avoids a known-only enqueue failure oracle. Receipt/address identifiers are purpose-separated HMACs; no raw unknown email is retained. Timing equivalence and distributed IP/global/login/MFA abuse defense are not established.

Reset token is 32 CSPRNG bytes, SHA-256 lookup only, single-use, DB-clock expiry. The delivery copy and eligible recipient exist only in a versioned AES-256-GCM payload with random 96-bit IV, authenticated outbox ID, and HKDF-separated encryption/receipt keys from a distinct 32-byte AUTH_RECOVERY_KEY. No plaintext token URL in persistent rows, logs, errors or response DTOs. Key stays server-only and stable across restarts; no automatic key creation/rotation. `/recover#token=...` keeps the token out of HTTP paths/queries/Referer; the client removes the fragment from current history and submits it only in the reset POST body. This does not erase inbox/browser extensions/history synchronization or protect a compromised device. Request-body capture must be disabled in an eventual host/sender.

Outbox: SKIP LOCKED claim, random lease ID, 30-second lease, maximum 3 claims, 5-second adapter deadline, retry delays 30 then 120 seconds; ack/fail require the current unexpired lease. Expiry/consumption cancels jobs, terminal states clear ciphertext. A crashed last attempt becomes failed on the next drain. The [explicit local CLI](../../src/modules/auth/recovery-drain-cli.ts) drains at most 10 jobs, reports sanitized aggregate states/error counts/oldest age, and removes recovery-only rows older than one day after expiry (receipts after one day). It is a **synthetic discard adapter**, not an email worker or production scheduler. Tests inject an in-memory mail sink. No SMTP/HTTP sender, external email, public outbox inspection/retry API or automatic background scheduling exists.

## Alternatives and consequences

Baseline recovery 503 remains the fallback when no recovery key is configured. Keeping it forever would not meet recovery acceptance. Native reset plus a later onPasswordReset hook was rejected for this slice: a post-update callback cannot prove the same transaction for app version/revocation, and does not serialize proof/session attachment. Native plaintext verification/delivery payloads and in-memory queues do not meet this storage/restart contract. A second provider or password implementation adds migration/operational burden without evidence of need. Managed Auth0 remains the conditional broader DEC-001 fallback, requiring separately authorized provider validation.

At-least-once delivery can duplicate a message after a lost ack/crash; adapter idempotency uses the stable outbox ID, and repeated messages carry the same single-use token. An already in-flight message may arrive after reset/expiry and be unusable. A future adapter must honor AbortSignal; a timeout cannot unsend a message or forcibly stop an uncooperative external service. DB outage/commit uncertainty produces 503, never assumed success. If reset committed despite response loss, token retry fails: try the new password or request another link. Already authorized responses can be in flight; subsequent authorization denies after successful reset. An outage before commit can leave the old password/session valid after recovery. Lost keys block pending delivery; no secret dump or plaintext fallback.

Costs remain unverified: no paid resources/accounts provisioned. Real sender selection, commercial terms, hosted budget, legal/retention review, secret management/rotation and operator recovery ownership are user-owned release dependencies. Routine local SQL/API/UI choices do not require separate approval. Reconsider for provider upgrade/schema changes, new auth entry points, multi-replica throughput or approved delivery/hosting. Keep DEC-001 open until every register criterion has concrete evidence and approval.
